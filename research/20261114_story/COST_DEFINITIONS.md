# Cost measurements and their scope

The implementation emits signed events with eight threshold-dependent magnitudes. One nonzero scalar output of an MTH site is one scalar event; positive and negative events are counted separately. A graph-convolution branch event and an MLP event have different downstream consumers. Counts do not include residual skip values as if they were additional binary spikes. Nonzero events do not trigger sparse kernel dispatch: the current PyG implementation executes every dense projection and graph edge at every tick.

`benchmark_cost.py` measures the actual shared calibration-core implementation on one fixed, cached 32-graph validation batch per task, with 10 warmups per condition, 30 randomized interleaved measurement rounds, CUDA synchronization immediately before/after each measurement, and all raw batch times retained. Median per-graph milliseconds are batch milliseconds divided by 32, not individually timed graphs. Host-to-device transfers and dataset loading are excluded. Every converted condition returns decoded site activations as well as logits. Those extra site accumulations are part of this diagnostic implementation, so the measured teacher/converted ratio is not a best-achievable deployment bound. Teacher uses the same full frozen architecture and graph batch. Deterministic algorithms are enabled in both.

The dense-operation ledger is an explicitly partial lower bound on arithmetic, with MAC defined as one multiply-accumulate pair, not one FLOP. Per tick it includes embedding and graph/MLP projection MACs, edge-weight multiplication, graph scatter addition, residual addition and pooling scatter addition. It excludes eight-level membrane/comparison arithmetic, biases, normalization setup, decoding, allocation and memory traffic. Therefore it cannot be used as a complete energy denominator or to claim arithmetic savings. The event-count records allow independent inspection of positive, negative and zero events at each site/tick; sparse events do not reduce the recorded dense-kernel work.

Offline costs are separate: optimizer-update time includes the backward pass, offset update and clamping, with synchronization; the reported peak allocated CUDA memory also includes cached calibration batches and teacher targets. New confirmation metadata additionally records data/hash checking, model/data loading, target caching and acceptance setup as a shared preparation cost. Total run time includes all validation evaluations and is not solely calibration time. Original screen setup was not separately timed.

No dedicated hardware energy measurement was performed. No joule reduction, binary-spike AC/MAC energy conversion or neuromorphic speedup is inferred from these measurements. A future complete arithmetic/energy model must charge the signed-level selection, all state updates, encode/decode, biases, normalization and memory costs before comparing with a teacher implementation on the target backend.
